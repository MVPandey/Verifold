## Recommendation

Adopt Automative as an optional execution adapter and borrow its deterministic contract, evidence log, and memory patterns. Keep Verifold's canonical run manifest independent of the harness. This preserves the explicit decisions in [founder context](../../verifold-context.md), sections 3, 4.1, 6.2, and 17: neutral infrastructure, pre-registration, review by rerun, and no proprietary harness as the wedge.

The requested profile → daily discovery → pilot → approved experiment → shared findings journey fits those decisions if ideas remain hypotheses, pilots remain exploratory, and only separately validated runs earn verification status. The latest request broadens discovery to science interests; launch execution can still remain computational ML as the existing context specifies. Community can start with shareable run pages and fork lineage while social ranking waits for a corpus.

## Boundaries to strengthen for a research hub

These are design inferences from the inspected implementation, not claims that Automative promises a distributed scientific platform.

1. **Optimization success is not scientific verification.** `decide.py` compares a scalar against the incumbent; `heldout.py:paired_check` evaluates one candidate and one incumbent measurement. Neither alone establishes fresh-seed replication, statistical significance, independent execution, or scientific relevance. Verifold must distinguish “pilot promising,” “criteria met,” and “independently reproduced.”
2. **Repeated held-out feedback remains information.** Returning only pass/fail reduces disclosure but allows adaptive selection over repeated attempts. Reserve independent final evaluation data/seeds, record the query budget, and define the testing policy before confirmatory execution.
3. **Hooks and audit logs are not a security boundary.** Automative's own [sealed-verifier documentation](https://github.com/MVPandey/Automative/blob/a7d72de784b01a853fb9a4135942a808268f805e/docs/SEALED-VERIFIER.md) explicitly describes same-user access and the residual sanctioned-command escape. Run candidate code in isolated workers; keep verifier data and credentials outside that worker's accessible mounts and identity. Audit is useful evidence but cannot establish visibility into every indirect child-process file read.
4. **Local JSONL and a local lock do not provide distributed durability.** `ledger.append` writes JSONL; `state.run_lock` uses an advisory process lock; held-out comparison temporarily swaps files in one working tree. A hosted scheduler needs durable jobs, transactional event sequencing, idempotency keys, isolated workspaces per attempt, and crash reconciliation. Export events into Git; avoid multiple agents directly editing one JSONL file or branch.
5. **Hashes establish consistency, not independent attestation.** A worker with write access can potentially rewrite local evidence and its hashes. The hub should receive append-only events through a separate identity, retain immutable artifact hashes, and record verifier identities and replication provenance.
6. **Memory attribution is suggestive.** `record_evidence` credits all cited strategies from an attempt's verdict. That is useful retrieval metadata, not causal proof that each strategy helped. Separate reported lessons from ablation-supported findings.
7. **A single incumbent is too narrow for all research.** Preserve the optional greedy loop for cheap optimization. General research needs experiment DAGs, parallel baselines and ablations, contradictory findings, and informative negative results. A negative scientific finding must remain publishable even when an optimization attempt is discarded.
8. **Local session context requires selective import.** The user asks to link agentic coding sessions. Import an explicit session/export or selected project scope with provenance and redaction; do not make local sessions globally shared strategy memory by default.

## Suggested platform boundaries

- **TypeScript domain layer:** profile, source reference, idea, pilot, approved plan, run, event, artifact, verification, contribution. Keep lifecycle transitions and gate evaluation pure and tested.
- **Application services:** daily discovery, idea deduplication and ranking, pilot preparation, plan approval, run scheduling, budget authorization, publication.
- **Ports/adapters:** paper providers, identity/profile import, model providers, Automative/autoresearch, compute providers, repositories, notifications.
- **Execution plane:** isolated workers with scoped capabilities and lease/heartbeat reporting. The planner assigns task ownership and dependency edges; the server controls budgets and state changes.
- **Evidence storage and UI:** durable event stream plus object storage; run pages and reports are projections. Shared Markdown notes remain readable exports, not the sole authoritative state.

An Automative adapter should ingest the contract, `run_start`, `iteration`, `shown`, and `run_end` records; map commits and logs to Verifold artifacts; preserve the upstream decision separately from Verifold's scientific verdict; and record the imported harness version. Start with import/export before remote execution to validate the record model cheaply.

1. Should launch execution stay within computational ML, with broader science interests used only for discovery, or is cross-domain execution an explicit scope change?
2. Is Automative the first supported personal execution backend alongside an autoresearch importer, or should the first pilot be entirely hosted?
3. What qualifies a run for the first verification badge: fresh-seed rerun by the same worker, a separate verifier identity, or independent hardware/operator?
4. What pilot spend and recurring monthly spend may the system authorize automatically, and where must a person approve escalation?
5. Which local agent sessions should contribute to personalization, and should private findings ever inform shared community memory?
6. Should the first user-facing result optimize for actionable private R&D, publication-ready evidence, or a reusable open project? The acceptance template and report should follow that purpose.
