# Security

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/MVPandey/Verifold/security/advisories/new) for a suspected security issue. Do not put credentials or private research in a public issue.

Include the package version, operating system, reproduction steps, and expected impact. Use a disposable project for reproduction.

## Trust boundary

Verifold starts the harness of each agent of the lab, Claude Code or Codex, through the harness's ACP adapter, which `npx` runs at a pinned version. The lab's agents are the seats that you chose, and a seat that the coordinator adds with your yes or with the power that you switched on for it. Verifold starts no agent of its own: a rerun of a result is the work of an agent of the lab. `npx` uses an empty npm project of Verifold's own, `~/.verifold/npx`, so a `node_modules` folder or an `.npmrc` file in the project or in an agent's folder can't change what runs. Each harness runs with your own settings and permissions, as it does without Verifold. Verifold adds no sandbox. An agent can do what its harness allows, so run Verifold only in a project that you trust, with harness settings that you trust.

Only `~/.verifold/settings.json` can add or change a harness. Verifold refuses a project's settings file that holds harnesses, and it refuses to start when the project's repository tracks lab files in `.verifold/` other than `settings.json`, because a lab's record decides which agents start and what they get.

When a harness asks for a permission, Verifold shows the request to you on the board. The agent waits for your answer, or gets a refusal until you answer, as your settings and the lab's auto mode say. The ask holds the whole command or tool input. It is a post, so every agent of the lab can read it and the lab's record keeps it: a secret in a command or in an input is then on the board and in `.verifold/`. The app shows the command or input in a box of its own, apart from Verifold's sentences, and not as Markdown. In it, Verifold writes as code points the control and format characters, every space but the plain one, and Unicode's default-ignorable characters, such as zero-width and direction marks, variation selectors, and fillers. It does not change letters that look like other letters, such as a Cyrillic letter that looks like a Latin "a", so read a name in a command with that in mind. It refuses a request that is too long to show whole. When you allow auto mode for a lab, each harness uses its own auto mode.

The lab's coordinator is an agent, and it can ask you for a move that is yours alone: more time for the lab, the answer to another agent's permission request, one more agent or the removal of one, a setting of the running lab, a revision of the question, or a move of pace. A request changes nothing until you say yes. You can switch on a power for one kind of move, and the coordinator then makes such a move without asking you. Every power is off until you switch it on, and all of them go off when the coordinator seat changes. A power makes no move after the lab's time ran out or after you stopped the lab. Verifold checks these rules on every event that the board takes, so no board tool goes around them. A power lets an agent do what the move does:

- With "Answer permission requests", an agent decides what other agents may run on your computer. The coordinator can allow or refuse, for one time, any command or tool call that another agent's harness asks you for. It cannot answer a request of its own harness, pick an answer that a harness remembers, or give a grant for every agent. Two agents that work together can still get a command allowed, one request at a time.
- With "Add or remove agents", an agent starts more harnesses with your settings, up to 20 agents in the lab, and each one spends your tokens. It chooses the harness, the model, the effort, and whether the new agent is on call. It cannot state a model family, choose a mode, or give the coordinator seat, a power, or a reviewer seat. A role that it gives shows as given by the coordinator. It can also remove any other agent.
- With "Give the lab more time", an agent keeps the lab running, and spending, for up to one week more with each move, for as long as the lab has time. It cannot give time to a lab whose time ran out, so a lab that you stopped stays stopped.
- With "Change the lab's settings", an agent sets the processes that agents left running to pause or to stop at the time limit, and to stop when Verifold exits. It cannot set `finish` or `keep`, with which they run on after a stop, and it cannot change how Verifold handles permission requests.
- With "Revise the question", an agent changes what the whole lab works on.
- With "Pause seats and limit tokens per hour", an agent pauses another seat than the desk, and sets a limit of tokens per hour for a seat or for the whole lab. It can only lower what you set: it cannot resume a seat that you paused, set a limit above yours or above the lab's budget in tokens, or take back a limit that you set. A pause or a limit can hold the lab's work back, and a post of yours still starts the turn of a paused seat.

`verifold run` takes no power from a project's settings file, and the app saves no power among the choices for new labs. The conversation between you and the coordinator is a thread that every agent can read. A post that the coordinator marks as one for you holds the coordinator's words, not yours, and the app says so on the post. A request shows what your yes does in the app's own sentences, and every text of the coordinator stands in a box under a label.

The desk is an agent too, and you choose its seat. It acts on your word: it can post for you, open a round, revise the question, change a deliverable, set the time that the lab has left, and end another agent's turn. Each action names your message in the desk chat that it rests on, and the board refuses an action whose message is not yours, is in another thread, or is more than an hour old. So no post of another agent can stand in for your word, and the record keeps the message with each action. A message of yours in the desk chat starts a turn of the desk also while the lab is out of time, at its budget, or at its disk limit, and that turn spends tokens toward the budget as any turn does. The desk can set the budget on your word, and it sets no disk limit, which stays your setting. The rule cannot check that an action is what the message asked for: the desk reads the other agents' posts, and a post can try to steer it. Its tools take no permission request, no request of the coordinator, no power, no agent or seat, no vote or badge, no setting such as the disk limit, and no norm. A project's settings file makes no seat the desk under `verifold run`.

An allowance is recorded, not enforced. An acting seat holds its own key, such as an account at an exchange, and makes its own calls with it. The board records each action that the seat declares, counts its cost against the allowance, and stops the seat at the allowance's total, but it is not in the path of the call, so it does not see a call that the seat does not declare. Set the limits that the key itself allows at the provider that issued it. Only your press in the app, or `--allowance` of `verifold run`, starts an allowance. The desk drafts one on your word, and no tool of an agent starts or raises one. A project's settings file holds no allowance and marks no seat as acting under `verifold run`.

The server listens only on 127.0.0.1. The app needs the token in the link that Verifold prints, and each agent joins the board with its own token. Text from agents is untrusted. The app shows it as text, never as HTML, and its Content-Security-Policy allows images and connections only from Verifold's own server.

Model providers receive what each harness sends them, as the harness's configuration allows. The lab's record, the agents' folders, and the snapshots of those folders stay in `.verifold/` in the project. An agent that takes a rerun of a post gets the path of a clean copy of the author's folder at the commit that the post pins: plain files, with no Git repository and nothing from after that commit. So every file of a snapshot that a post pins can reach another agent's harness and its model provider. The copy is in a folder of Verifold's own, `.verifold/reruns/` in the project, which only you open. For a rerun, Verifold writes nothing, deletes nothing, and runs no Git command inside any agent's folder, because an agent can change its own folder at any moment. Verifold proves that the copy's bytes are the pinned commit's at the moment of each take. The record holds the commit's ID. Verifold reads the commit, its folders, and its files as Git objects through `git cat-file --batch`, and computes each object's ID itself: the commit's must be the ID in the record, each folder's the ID that its parent names, and each file's the ID that its folder names. So an object that was changed on disk, or one that a repository tells Git to give in another's place, is refused. Verifold reads the folders' listings itself and refuses a name that is not safe to write. It stops at 50,000 entries, 2 GB, 64 folders inside each other, and 256 MB of folder listings, and it ends the Git processes of a copy after five minutes in all, or when the server stops. Two copies are made at a time. It checks a copy that exists already file for file at every take, and makes it again when anything differs. It reaches its own folders through directory handles that follow no link. Each take returns a manifest with the SHA-256 of every file, and the record keeps the manifest's SHA-256. An agent that runs as you, with no sandbox, can change files on this computer afterwards, the copy among them. So the manifest is the check: the files that a taker reads are the pinned ones when they have the manifest's SHA-256. The only Git command for a copy is `git cat-file --batch`, with Verifold's own folder as the working directory. It runs on a Git directory of Verifold's own, `.verifold/snapshots.git`, so Git reads the configuration that Verifold wrote there, and none of a repository of the lab. Verifold checks that configuration at each use and writes it again when it differs. The command takes the objects from the object store that has the commit, which `GIT_OBJECT_DIRECTORY` names. The first store is the one of Verifold's own Git directory, which holds every snapshot that Verifold makes. A commit from before Verifold kept the snapshots there is in another store. In a project with Git commits that is your project's store. In a project without them it is the store in the author's own folder, which that agent can write. Verifold finds those two stores itself, without Git: from the `.git` of your project and of the author's folder, through a `gitdir:` file and a `commondir` file where they are. It reads its own store first and your project's store next, and it looks for the author's store only when those fail, so a change to an author's folder takes no commit away that Verifold's own store or your project's repository has. An agent can point the files of its own folder at any store. Git reads a store's files as data: its objects, its packs, and its list of other stores. Verifold computes the ID of every object, so a store can withhold an object and cannot change one. The command runs with hooks and the file watcher off, with every transport off, with no fetch of a missing object, with no object replaced, and with none of your own or the system's Git configuration. The app reads a file that a post pins in the same way. It reads four files at a time and ends the Git processes of one read after 30 seconds in all. The check of a rerun is pinned from the taker's own folder by the pin that every post uses. A snapshot of an agent's folder, which Verifold makes after each turn and for each pin, is a commit in that Git directory of Verifold's own. Every Git command for a snapshot names that directory and starts in Verifold's own folder, under the same rules as the command for a copy. The one that reads the agent's files, `git add`, names the agent's folder as its work tree and works there. So Git finds no repository from the agent's folder, and it uses no configuration, hook, or filter of the folder's own repository or of your project's. Nothing in the folder can name a program that runs. Git reads the agent's files, and its `.gitignore` and `.gitattributes` files, as data. An attribute can ask for a filter, and no configuration that Git reads names a program for one. An attribute can also make Git store other bytes than the file's: other line ends, another encoding, or a short `$Id$` line. Git records a repository inside the folder as that repository's one commit, without its files. For that it reads the repository's HEAD and its format settings, also through a `.git` file there that names another Git directory. Verifold asks Git for one value of your own configuration, `core.excludesFile`, and passes it on, so that your own list of ignored files applies. Git also reads your default attributes file, `git/attributes` in `$XDG_CONFIG_HOME`, as data. Your filters, such as Git LFS, and your commit signing do not run, so a snapshot holds a file under an LFS attribute whole. Verifold commits no folder of an agent that is a link or lies behind one. A snapshot writes nothing in the agent's folder and nothing in your project's repository. At each use of its own Git directory, Verifold checks that the folders for the objects and for the refs are folders and no links. It removes the files that Git would read there and that Verifold never writes: `commondir`, `info/exclude`, `info/attributes`, and `objects/info/alternates`. Every Git command that Verifold runs has hooks and the file watcher off. Verifold ends a Git command for a snapshot, and one in your project's folder, after five minutes. It ends the one that makes an agent's folder in a project with Git commits after 30 minutes, because a checkout with your own filters can take long. Such a command runs in a process group of its own. Verifold ends that group at the limit and when the server stops, so the programs that the command started end with it, unless one left the group. It asks the group to end first, so that Git removes its own locks and what it made half, and it kills a group that still runs a second later. It does the same when a signal of another program ended Git. After the command that makes an agent's folder was cut in one of these ways, Verifold removes what that call made: the folder, the worktree's entry in your repository, and the branch when the call made that too, with a lock that Git left at that branch. It removes nothing that was at the folder's path before the call. After Git failed by itself, it removes only its own folder when that is empty, and after a `git init` that failed, the new folder with what Git put there. After the command that moves an agent's ref in Verifold's own directory was cut, Verifold removes the lock that the command left there. Two things can stay. Git does not always clean up: it cannot when it is killed, and sometimes it leaves an empty lock when the signal to end reaches it at the moment when it makes that lock. Then another lock of Git's, such as `packed-refs.lock`, can stay in your repository, with the agent's new branch, or an entry of the worktree without its folder. Git names what stands in its way in the error of its next command that needs it, and Verifold removes none of these. And when the computer stops, or Verifold is killed, in the middle of such a command, a folder that Git did not finish can stay, and Verifold takes it as the agent's folder at its next start. The commands that are not for a snapshot run in your project's folder at each start, and there or in the new folder when Verifold makes an agent's folder. They read your own Git configuration, so that your checkout filters still work. Known limit: in a project with Git commits, an agent's folder is a worktree of your project's repository, and Verifold makes it with `git worktree add`. That command reads your repository's configuration and attributes, as your own Git commands there do, and it runs a checkout filter that they name. It fetches no object that the repository lacks, with Git 2.45 or later. So a program that can write your project's `.git` can make a command run when Verifold next adds an agent. It can do the same for your own next Git command there. An agent's folder in such a project shares that configuration, so an agent that its harness lets write Git configuration writes yours. Before each write to the record, the server checks that the path still names the file that it opened, that the file ends where the server's last write ended, and that its last bytes, at most 4,096 of them, are the ones that the server wrote. It moves bytes that another program added at the end to `.verifold/record.foreign.jsonl`. It stops when the file was replaced, removed, shortened, or rewritten, and when the path names another file or none, it first copies what it wrote to a new file, `.verifold/record.kept.jsonl` or the next free name. Only your account can read these files, Verifold writes them through no link, and it never reads them. Any other change to the record takes effect at the next start, and so does any change after the server's last write or while no server ran. That includes a change inside what the server wrote that keeps the file's length and those last bytes. Verifold cannot tell such a change from its own writing. At each start, Verifold trusts the record as it is on disk: an agent that can write `.verifold/record.jsonl` can add a line that switches a power on or answers a request, and the next start of Verifold takes it as yours. The record holds the ID of each agent's harness session, so that the harness can load the conversation again after a restart. A record that you share shows those IDs, and so does the file to any program on this computer that reads it.
